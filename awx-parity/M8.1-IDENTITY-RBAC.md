# M8.1 — Identity, SSO and authorization baseline

Status: **implementation checkpoint complete for handoff; automated and manual verification outstanding; HA explicitly out of scope**. Base: fork `develop` at `28d157bf` (2026-10-22). This branch must not import `feature/postgres-ha`.

## Verified in the Community source

- `api/auth.go`: cookie-backed database sessions, inactivity and absolute expiry, TOTP recovery and login audit integration.
- `api/login_identity.go`: OIDC/LDAP external identities are keyed by provider and stable external UID. Verified-email matching is guarded; local password accounts are not adopted by external identities.
- `db/Role.go`: distinct instance-wide and project role permission models; project template role permissions exist.
- `db/RoleMapping.go`: project role mapping from IdP groups is modeled.
- `api/global_permissions.go`: permission middleware and protection against non-admin edits of more privileged accounts; Community global-role store may return no grants.
- Documentation confirms existing OIDC, LDAP/AD and local login. Do **not** reimplement these without a failing test or demonstrated gap.

## What remains to inspect and verify

1. Trace OIDC claims and group synchronization through callback, persistence and permission checks, including revocation after group removal.
2. Trace LDAP group mapping and group sync, including deletion/deprovisioning.
3. Check Community-vs-Pro gates for role mappings, custom roles, global roles and API routes. Data models alone do not prove usable Community functionality.
4. Determine whether native SAML 2.0 exists. If absent, evaluate a SAML-to-OIDC broker (Keycloak) first, then native SAML only if required.
5. Audit CSRF/state/nonce/PKCE, redirect allowlisting, cookie flags, session invalidation, account linking and IdP logout behavior.
6. Define service-account and API-token scopes, separate task-execution rights from credential-management rights, and test authorization for API + UI.
7. Add provider integration tests (Keycloak OIDC, LDAP), role-revocation tests and permission-denial audit tests.

## Security invariants

- Authentication and authorization are separate. A successful SSO login grants no project privileges by default.
- Provider + stable external subject identifies an account; unverified email never grants account linkage.
- Group removal must revoke effective privileges; failed group synchronization must not silently retain newly asserted privileges.
- No self-escalation via group mappings, template roles, user editing, tokens or delegated administration.
- Preserve a protected, audited break-glass local administrator.
- Prefer existing Community APIs and migrations over a parallel identity database.
